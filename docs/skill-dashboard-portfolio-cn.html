Problem Statement

用户的 AI 能力已经存在，但仍然不可调用

项目的起点不是做一个“更好看的技能列表”，而是回应一个真实的认知断层：用户装了很多能力，却依然不知道自己拥有什么、该从哪里开始、哪些资产值得整理。

!

装了很多，但说不清

目标用户已经在 Cursor、Claude、ChatGPT 等环境里安装了大量 skills 与 prompts，但缺乏一眼可见的总览。

#

文件名不是能力模型

文件路径、目录名和 Markdown 原文不能直接回答“它能做什么、什么时候该用、值不值得保留”。

?

知道有资产，不知道怎么选

当数量超过 10 个之后，用户开始依赖模糊记忆，反复翻找文件，甚至重复造轮子。

~

现有工具只存，不解释

Prompt Manager 更像仓库，文件浏览器更像目录树，而 Skill Dashboard 试图先把资产翻译成可理解的能力卡片。

Target Users

为“有资产但没地图”的用户设计

PRD 明确把核心人群定义为非技术背景的 vibe coding 爱好者。他们的问题不是不会安装工具，而是不会管理、检索和复用已经拥有的 AI 资产。

Primary

Vibe Coding 爱好者

用过 Cursor / Claude / ChatGPT，跟着教程安装过一批 skills、prompts 和 SOP，但已经开始出现“装完以后找不到”的疲劳感。

  • 快速看见自己当前拥有哪些能力
  • 按任务而不是按文件名找到合适资产
  • 把常用资产留住，把混乱资产理顺
Context

项目创作者本人

既是构建者也是使用者，因此第一版无需权限体系、多用户协作或云同步，重点转向个人资产治理的真实闭环。

  • 验证产品是否能在本地独立跑通
  • 在不破坏原文件的前提下补充展示层
  • 为后续跨平台扩展打统一模型基础
Insight

产品洞察

大多数 AI 工具都在帮助用户“获得新能力”，而这个产品选择反过来，帮助用户“盘活已拥有的能力”。

  • 让资产从“存在”变成“可调用”
  • 让整理动作有明确入口和反馈
  • 先做认知基础，再谈执行与编排
Phase One

第一阶段先完成“集中展示 + 可检索”的基础闭环

这一阶段不追求一步到位的治理系统，而是先把分散在本地的 AI skills 集中到一个工作台里，让用户能够稳定看见并快速检索。

1

扫描本地目录

从 Codex skills 目录开始，逐步扩展到多平台 AI 资产白名单。

从“我记得装过”变成“系统真实发现”
2

统一解析模型

把 skill、rule、prompt 等差异化命名统一抽象成 `AIAsset`。

解决“各平台名字不同，无法统一看”的结构问题
3

展示真实数据

前端不再依赖纯 mock，而是展示解析后的真实技能卡片与状态。

让页面从概念展示走向可信产品
4

健康检查发现缺口

识别缺少描述、来源不明、结构不完整等问题，把“看见”连接到“该整理什么”。

让总览页不只是列表，而是治理入口
5

sidecar metadata 持久化

补充信息只写入 `metadata.json` 或 sidecar 记录，不改原始 `SKILL.md`。

兼顾安全边界、可编辑性与刷新后保留
User Stories

产品如何把“认知断层”拆成具体需求

这些用户故事不是装饰性文案，而是从 PRD 和 Alpha 真实链路里反推出来的关键动作，帮助页面把抽象愿景落到用户任务上。

作为已经安装了很多 AI 资产的用户
我希望快速看清本地已经有哪些能力
以便不再依赖模糊记忆翻目录，先建立全局认知。
作为不知道从哪个 skill 开始的用户
我希望看到一句话描述、分类和适用场景
以便把“文件名”转换成我能理解的能力标签。
作为面对英文技能资产的中文用户
我希望系统能生成中文展示层
以便更自然地检索、理解和复用这些资产，而不是直接阅读英文原文。
作为担心破坏原文件的用户
我希望补充信息只写到 sidecar metadata
以便安全地整理和中文化，而不影响原始 skill 文件的完整性。
Key Features

先把“集中 + 检索”做扎实，再扩展后续能力

当前版本优先围绕工作台总览、统一展示和搜索检索展开，让用户先解决“找不到”的问题，再逐步进入分析、整理与治理场景。

Discovery

技能卡片总览

把原本散落的本地资产整理成可浏览的能力卡片，突出名称、描述、分类、场景和来源等关键信息。

Structure

搜索与分层筛选

支持按关键词、分类、来源和使用阶段筛选，让用户从“知道有很多”走向“找到当前正需要的那个”。

Analysis

健康检查与问题摘要

识别来源未知、描述缺失、疑似重复等治理问题，把总览页自然导向分析和整理动作。

Localization

中文展示层

为英文原始 skill 生成中文标题、描述、标签与适用场景，优先服务中文用户的理解和检索。

Safe Edit

sidecar metadata 持久化

所有补录和中文化结果都写入 sidecar 数据层，而不是改写原始资产文件，建立清晰的数据安全边界。

Overview / Analysis / Organize

信息架构分工

首页看全貌，Analysis 看结构，Organize 做动作，避免首页既像文件管理器又像告警中心的职责混乱。

Product Decisions

为了先把核心价值做清楚，第一阶段刻意收窄边界

如果第一版同时追求治理、执行、编排和市场安装管理，页面会很完整，产品却会失焦。因此项目优先把“工作台集中展示 + 随时检索”这件事做透。

不改原始 `SKILL.md`

所有中文化、补录和来源确认都通过 sidecar metadata 完成。这样既保留原始资产的完整性，也降低了用户对“整理动作会不会破坏文件”的心理门槛。

  • 安全边界清晰
  • 可编辑结果可持久化
  • 刷新后状态可保留

不做技能执行层

MVP 阶段明确不接入技能执行或复杂 LLM 编排，因为当下用户最先缺的不是“运行”，而是“知道自己有什么”。

  • 避免执行层复杂度爆炸
  • 聚焦认知问题而非自动化炫技
  • 为后续 workflow 留出产品顺序

先支持白名单平台

V1 只扫描官方文档明确、路径稳定、用户价值高的本地目录。这个限制不是保守，而是为了让“识别到的都可信”。

  • 先保证路径识别的高置信度
  • 减少猜测式扫描带来的脏数据
  • 为统一模型打坚实基础

先总览，再分析，再整理

把页面拆成 Overview、Analysis、Organize，是因为用户第一次需要的是全局感，第二步才是看懂问题，第三步才是执行治理动作。

  • 首页建立规模感和结构感
  • 分析页承担诊断职责
  • 整理页承接补录与归档动作
Technical Architecture

技术结构服务于产品承诺，而不是反过来

技术方案围绕一个核心承诺展开：既要扫描真实本地资产、支持中文展示与补录，又不能冒险修改原文件。因此系统采用“原始解析结果 + sidecar metadata 覆盖结果”的双层数据模型。

安全性

通过 sidecar metadata 覆盖展示层，而不是直接改写 `SKILL.md`，系统把“内容理解”和“原始资产”解耦，降低了整理行为的破坏风险。

可扩展性

通过 `AIAsset` 统一模型，产品不再依赖某一个工具是否也使用 skill 这个名字，而是可以持续纳入不同平台的本地 AI 资产。

产品一致性

Overview、Analysis、Organize 三层信息架构与后端的扫描、分析、补录能力一一对应，让页面结构和系统能力保持同向演进。
